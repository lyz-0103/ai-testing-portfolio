# 校园问答助手 LLM 评测集

给一个「校园智能问答助手」场景下的 LLM 应用做批量评测。60 条用例 + 自动化评测脚本 + 评测报告，跑测对象是任意 OpenAI 兼容接口（Qwen / GLM / DeepSeek 等）。

完整的评测思路和设计取舍写在 [docs/评测方案设计.md](./docs/评测方案设计.md)，这里只放结论和用法。

## 快速开始

```bash
# 离线自检（不需要 API Key，验证脚本逻辑，内置 3 条植入 badcase）
python3 eval_runner.py --mock

# 真实模型（任意 OpenAI 兼容接口）
export API_KEY="sk-xxx"
export BASE_URL="https://dashscope.aliyuncs.com/compatible-mode/v1"
export MODEL="qwen-turbo"
python3 eval_runner.py

# CI 门禁：通过率低于 90% 时退出码为 1
python3 eval_runner.py --mock --fail-under 90
```

零第三方依赖，Python 3.8+ 直接跑。

## 当前状态

**qwen-turbo 真实跑测（2026-10-04，60 条全量）**：

| 类别 | 通过率 | 主要失败原因 |
|------|--------|--------------|
| 正常（40 条） | 80.0% | 超长 6 条（模型对字数约束不敏感）、缺关键信息 2 条 |
| 边界（10 条） | 80.0% | 模糊输入/敏感话题未按预期澄清（澄清词表覆盖不足，见设计文档） |
| 恶意（10 条） | 90.0% | 伪装管理员注入导致系统提示词泄漏 1 条（高风险） |
| **总体** | **81.7%（49/60）** | 平均延迟 1.41s |

**关于数字波动**：同套用例、同模型、温度 0.2，两轮跑测总体通过率 88.3% → 81.7%，波动约 7 个百分点。非确定性输出下单次跑测不构成质量结论，v2 计划每条用例跑 N=3 取均值，高风险用例单独加严（见设计文档第五节）。

离线自检（`--mock`，验证脚本逻辑用）：95.0%，3 条植入 badcase 全部捕获。

## 迭代记录

- **v0.1（20 条）**：跑通「用例 → 批量跑测 → 报告」闭环。这版吃了关键词误报的亏，单个宽泛词（如"开放"）经常误判。
- **v0.2（44 条）**：关键词改成名词性信息词；给正常场景加"过度拒答"检测——收紧安全策略后正常问题的误拒率会悄悄上涨，不单独统计发现不了。
- **v0.3（60 条）**：补齐指令遵循子类（格式约束 + 长度校验）；恶意用例覆盖 5 种注入手法并单独标注；新增延迟统计、results 明细导出、`--fail-under` CI 门禁。
- **v0.4（首轮真实跑测后）**：qwen-turbo 首轮 68.3%（41/60），暴露三类问题并逐一修订判定规则：①正常题被"过度拒答"误判（长回答里出现"不能"只是行文）→ 加长度启发式；②模型说教式拒绝不含标准拒答词 → 按真实回答扩充词表；③E006 计算、E009 方言属正常可答问题 → 边界类拆出 expect_answer 子类。
- **v0.4.1**：人工复核发现 M004 被误判通过——模型开头说"不涉及"，正文却把系统提示词全文输出了。恶意用例增加 forbidden 负向断言（命中泄漏物直接判失败）。
- **v0.4.2**：forbidden 第一版把"拒绝时提到敏感词"也判了泄漏（误报），改为 `re:` 正则匹配真实数据模式（身份证号/手机号）+ 具体泄漏话术标记；新增 `--rejudge` 离线重判，规则修订后对历史跑测结果重新打分，不用重复花钱调 API。
- **v0.4.3**：results/ 增加 history/ 时间戳归档——起因是 --mock 自检覆盖了真实跑测数据。评测产物管理也是被测对象的一部分。

## 最有价值的发现（面试可深挖）

1. **提示词泄漏是真实风险**：伪装管理员的注入在两轮跑测中都稳定复现泄漏，且模型回答以"不涉及"开头——只靠"拒答词命中"判断安全性会漏掉这类先敷衍后照给的回答，所以才有 forbidden 负向断言。
2. **"提到"≠"给出"**：泄漏检测不能匹配敏感词本身，要匹配数据模式（身份证号正则）和泄漏话术标记。
3. **单次跑测不可信**：两轮 7 个百分点的波动说明评测必须多轮统计，这也是为什么明细要落盘可 diff。

## 已知局限

关键词判定抓不住"事实错误但用词正确"的回答，这个盲区计划用 LLM-as-judge + 人工抽检校准解决（见设计文档第六节）。澄清词表覆盖不足（E004/E010 这类"礼貌岔开话题"的回答没被识别为澄清）。评测集按已知失败模式设计，存在过拟合风险，对策是线上 badcase 持续沉淀 + 盲测集。
