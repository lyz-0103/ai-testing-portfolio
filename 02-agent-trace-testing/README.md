# Agent 工具调用轨迹测试 / 迭代上限护栏

给一个「校园助手 Agent」做测试。不一样的不是回答质量，而是**轨迹**：工具有没有乱调、会不会死循环、失败之后还敢不敢说"已经处理好了"。

15 条用例 + 零依赖评测脚本 + 可复现报告。完整的判定设计和取舍写在 [docs/评测方案设计.md](./docs/评测方案设计.md)。

## 快速开始

```bash
cd 02-agent-trace-testing
python3 eval_agent.py      # 零第三方依赖，Python 3.8+，不需要任何 API Key
```

脚本会跑完 15 条用例、逐条打印轨迹和判定、生成 `report.md` 与 `results/latest.json`。
被测对象在 `agent.py`，用例在 `eval_cases.json`，评估器在 `eval_agent.py`——三者是分开的，改哪一部分都不会连带影响另外两个。

## 这个 Agent 测的是什么

被测对象带三道护栏，用例就是围着这三道 + 四种错误路径设计的：

| 护栏 | 参数 | 触发后行为 |
|------|------|-----------|
| 迭代硬上限 | `max_iterations = 8` | 还没收敛就强制中止 |
| 单工具重试上限 | `max_retry_per_tool = 2` | 同一个工具连续失败 2 次，转人工 |
| 无进展窗口 | `no_progress_window = 3` | 连续 3 步工具 + 参数完全重复，提前中止 |

外加四个前置兜底：幻觉工具查注册表、参数 schema 预检、上游失败禁止给结论、轨迹耗尽必须显式 abort。

## 当前状态（v0.2，2026-10-04）

| 类别 | 用例 | 结果 |
|------|------|------|
| 正常（单工具 / 多工具 / 依赖参数 / 三步链路 / 类型约束 / 容错重试） | A001-A008 | 8/8 |
| 护栏（硬上限 / 无进展 / 工具连续失败） | B001-B003 | 3/3（另：B001 为缺陷探针，预期失败） |
| 错误恢复（参数缺失 / 幻觉工具 / 类型错误 / 上游失败却给结论） | C001-C004 | 4/4 |

- 整体 **14/15 = 93.3%**，有效用例（不含缺陷探针）**14/14 = 100%**
- 平均步数 3.20，三条护栏各被真实触发过：无进展中止 2 例、硬上限 1 例、工具转人工 1 例
- 缺陷探针 B001 永远应当 FAIL——它是评估器的回归哨兵，PASS 了反而说明护栏被改坏了

明细见 [report.md](./report.md)。

## 迭代记录

- **v0.1（15 条）**：跑通「用例 → 驱动 Agent → 轨迹判定 → 报告」。首轮挂 7 条，最严重的是 A008/B002/B003 **静默挂起**——轨迹跑完既没结论也没中止，生产上就是用户问了问题、Agent 一声不响。另外 C004「通知失败却说已通知」被当成正常通过。
- **v0.2（Agent + 评估器 + 用例三处一起改）**：
  - `agent.py` 补终态兜底（耗尽即 `PLAN_EXHAUSTED`）、幻觉工具前置校验、参数 schema 预检、迭代上限补 abort 步骤、上游失败禁结论；修正故障注入——原写法在参数合法时根本不注入失败，A007/B003 的容错路径等于从没跑过。
  - `eval_agent.py` 修正自己写错的判定：`required_calls` 原本无差别校验，把「预检就拦下、一次工具都没调」的 C001/C003 误判成漏调；新增「结论与轨迹一致性」维度；引入缺陷探针机制。
  - `agent.py` 加 `from __future__ import annotations`：`dict | None` 这种 PEP 604 注解在 Python 3.9 上是 import 期 `TypeError`，CI 的 3.11 和我本地的 3.13 都发现不了，只有你用本机 3.9 跑才会炸——所以这次特意用系统 python3 验了一遍。
  - `eval_cases.json` 按「护栏是否真的被触发」重排用例：A008/B002 补第 4 次重复让无进展窗口填满、B001 参数每次变化以绕开无进展窗口逼出硬上限并把 plan 加长到 22 条（否则兜底原因会错写成 `PLAN_EXHAUSTED`）、B003 补到 3 次让 `TOOL_GIVEUP` 生效。

## 最有价值的发现（面试可深挖）

1. **Agent 有两类挂起是 demo 看不出来的**：一类是轨迹耗尽后静默无响应，一类是上游工具失败了还给出结论。两种在功能演示时都恰好跑通了，只有跑轨迹才能发现。
2. **测「兜底逻辑」要先确认兜底真的被触发过**：无进展窗口是 3，用例只放 3 次重复调用时第 3 次刚好还没填满窗口，护栏压根没执行。用例条数写错，测了个寂寞。
3. **评估器自己也会错**：C001/C003 的失败是评估规则写歪导致的，不是被测对象的问题。判断是「对象挂了」还是「判定挂了」是这套流程里最值钱的一步。

## 已知局限

planner 是规则实现（不是 LLM）所以轨迹完全确定性、CI 不会假红；代价是接真实模型后要像项目 01 那样做 N 轮统计，并且要能识别规则脚本编不出的路径。另外没覆盖并发/幂等/长任务、final 内容不做语义级失真校验、护栏参数是拍脑袋定的没做阈值验证。详见设计文档第八节。
