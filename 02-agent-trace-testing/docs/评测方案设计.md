# Agent 测试方案设计（工具调用轨迹 / 迭代上限护栏 / 错误恢复）

## 1. 为什么单看「回答质量」测不出 Agent

普通 LLM 应用的评测对象是「一段文字」，拼的是准确率。Agent 不一样，它的产物是**一串动作**：

```
get_grade(张三, 高等数学)  →  ok
notify_advisor(张三, "考勤异常")  →  ok
final: "成绩已查并通知辅导员"
```

同样的结论，可能是三种完全不同的实现：工具真的调了、工具根本没调（编的）、调了但失败了还硬说成功。
所以这个项目的评测单位从「回答」换成了「轨迹」，判定也不再是关键词匹配，而是**结构断言**。

## 2. 被测对象

`agent.py`，一个最小可运行的校园助手 Agent，零第三方依赖：

| 组件 | 作用 |
|------|------|
| `TOOLS` | 工具注册表（5 个工具 + 各自的 params），工具幻觉的判定基准 |
| `execute_tool()` | 工具执行桩，参数不全 / 类型错 / 工具不存在都返回结构化 `{"ok": False, "error": ...}` |
| `AgentRuntime` | 迭代循环，受三道护栏约束：`max_iterations` 硬上限、`max_retry_per_tool` 单工具重试上限、`no_progress_window` 无进展窗口 |
| `run()` | 输出完整轨迹 `steps`、终态 `final` 或 `abort_reason` |

planner 用规则实现而不是接 LLM，是刻意的：同一份 `plan` 每次跑出来的轨迹完全一致，CI 里不会因为模型抖动出现假红假绿。真实 Agent 的 planner 不确定性留到下一阶段再补。

## 3. 用例分层（15 条）

| 层 | ID | 测什么 |
|----|----|--------|
| 正常 | A001-A008 | 单工具、多工具组合、依赖参数、三步链路、类型约束、容错重试，外加一条「护栏在普通场景下照常生效」 |
| 护栏 | B001-B003 | 硬上限兜死循环（参数每次都变，绕开无进展窗口）、无进展提前中止、工具连续失败转人工 |
| 错误恢复 | C001-C004 | 参数缺失、幻觉工具、参数类型错误、上游失败却仍给结论 |

`plan` 字段是 Agent 的逐步动作脚本（`call` 调工具 / `final` 给结论 / `abort` 中止），
`fail_inject` 声明「这个工具前 N 次调用强制失败」，用来测容错而不是测happy path。

## 4. 六个判定维度

| # | 维度 | 判定方式 |
|---|------|----------|
| 1 | 幻觉工具 | 轨迹里的工具名不在 `TOOLS` 注册表 |
| 2 | 参数合法性 | 静态比对 `params`，含 `book_room.duration_min` 必须是 int |
| 3 | 必需工具覆盖 | 预期收敛的用例，轨迹里必须出现 `required_calls`（中止类用例不校验，见 §6） |
| 4 | 迭代上限 | `steps_used > max_iterations`，疑似死循环 |
| 5 | 结论与轨迹一致性 | 最后一步工具调用失败却给了 `final`，属于掩盖失败 |
| 6 | 终态符合预期 | 预期 `final` 却中止 / 预期 `abort` 却给了结论，都算挂起 |

## 5. 首轮跑测（v0.1）发现了什么

第一次跑 15 条挂了 7 条，其中 3 条是最严重的：

| 用例 | 现象 | 性质 |
|------|------|------|
| A008 / B002 / B003 | 轨迹跑完既没 `final` 也没 `abort`，`abort_reason` 是 `None` | **静默挂起**——生产上表现为用户问了问题、Agent 一声不响 |
| C002 | 幻觉工具 `book_meeting_room` 直接进了调用，没被拦 | 工具幻觉只在事后我记得检查，工具内部才报错 |
| C003 | `duration_min="60"` 字符串类型错误，照样发出调用 | 类型约束没前置，全靠工具返回错误 |
| C004 | `notify_advisor` 失败了，下游照样 `final: "已通知辅导员（实际未送达）"` | **最危险的一类**：说谎 |
| A008 / B002 除了挂起，无进展护栏根本没触发 | 窗口是 3，用例只放了 3 次重复调用，第 3 次时窗口还没填满 | 测试设计没摸清护栏的触发条件 |

「静默挂起」和「说了没做」这两类，人工看 demo 基本发现不了——功能演示的时候恰好都跑通了。这也是我把 Agent 测试单独做一个项目的理由。

## 6. v0.2 修了什么（含判定规则自己错的地方）

被测对象（`agent.py`）：

1. **终态兜底**：for 循环跑完若既无结论也无中止，强制写 `PLAN_EXHAUSTED` 并 abort。静默挂起在 Agent 侧就没了。
2. **迭代上限也补 abort 步骤**：原来只改 `abort_reason` 不写轨迹，报告里看到的中止是「凭空出现」的。
3. **幻觉工具前置校验**：调用前先查注册表，不存在的工具直接 abort，工具幻觉不会进入执行层。
4. **参数 schema 前置校验**：缺参数 / `duration_min` 类型错，在发出调用前就拦下。
5. **上游失败禁止给结论**：放在 `final` 分支，失败就不许出结论。
6. **故障注入真的会注入**：v0.1 的写法只在工具自己报错时才减计数，合法参数的情况下注入形同虚设，A007/B003 的容错路径其实从没跑过。
7. **修一个只在 3.9 上炸的兼容性问题**：`run(self, case: dict, fail_inject: dict | None = None)` 里的 PEP 604 注解在 Python 3.9 是 import 期 `TypeError`，CI（3.11）和开发机（3.13）都跑得到，只有低版本环境会炸。改用 `from __future__ import annotations`。测试脚本的「能在我这台机器上跑通」和「能在我朋友那台老机器上跑通」是两回事。

评估器（`eval_agent.py`）：

1. **`required_calls` 只对预期收敛的用例校验**。C001/C003 本来就该「预检拦下、一次工具都没调」，v0.1 无差别校验，把它们误判成 FAIL——评估器自己写错了，不是被测对象的问题。
2. **新增「结论与轨迹一致性」维度**（第 5 条），这样即使 Agent 绕过兜底3 直接给 final，评估器也能从轨迹看出来。
3. **引入缺陷探针**：B001 是刻意植入的死循环缺陷，永远应当 FAIL。它不进通过率分母，作为评估器的回归哨兵——哪天它 PASS 了，说明护栏被人改坏了。

用例集（`eval_cases.json`）：

- A008 / B002 各补第 4 次重复调用，让 `no_progress_window=3` 真正填满、护栏真的触发（原来只靠兜底兜住，等于测了个寂寞）
- B001 参数每次都变以绕开无进展窗口，逼出硬上限；plan 加长到 22 条，否则第 12 步前轨迹就耗尽了，兜底原因会错写成 `PLAN_EXHAUSTED` 而不是 `ITERATION_LIMIT`
- B003 补到 3 次调用，`TOOL_GIVEUP` 才会触发
- meta 里「14 条 / 错误恢复 3」与实际 15 条 / 4 对齐

## 7. 修完的跑测结果（v0.2）

- 整体 14/15 = 93.3%（另 1 条为缺陷探针 B001，预期失败）
- 有效用例 14/14 = 100%
- 三条护栏各自真正被触发过一次：无进展中止 2 例（A008、B002）、硬上限 1 例（B001）、工具转人工 1 例（B003）
- 平均步数 3.20

## 8. 已知局限

1. **planner 是规则实现，不是 LLM**。真实 Agent 的轨迹由模型现场生成，会出现规则脚本编不出来的路径（比如工具返回的内容反过来影响下一步）。要接真模型跑，就得像项目 01 那样做 N 轮统计，否则单轮结果没有意义。
2. **静态 plan 无法自增重试**。用例里「重试」是靠手写重复的 `call` 实现的；真实 Agent 应该自己决定重试。真接 LLM 后这条要改成「轨迹里出现连续同参调用时判定是否在重试、是否该停」。
3. **判定是结构化的，没有语义级校验**。final 的内容对不对（有没有编造工具返回值）目前只查「有没有调对工具」，不查结论本身是否撒谎。
4. **没有并发 / 幂等 / 长任务覆盖**。预约类工具重复调用会不会重复建单、工具超时怎么兜，都还没测。
5. **护栏参数靠拍脑袋**：`max_iterations=8`、`no_progress_window=3` 是拍出来的，没有基于真实分布调参，也没有统计意义上的阈值验证。
